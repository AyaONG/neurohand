# Настройка Supabase и Google входа для NeuroHand

Этап 12 подготовлен локально на базе `2cc68ad` в `feature/neurohand-attempts`. Вход, разделение профилей, миграция и проверки готовы в репозитории. Настройки Supabase, Google Cloud и Vercel **ещё не применены и не проверены**: подключённых браузеров не обнаружено, публичные значения проекта и Production URL не предоставлены. В этапе 13 добавлена синхронизация финальных результатов при настроенном клиенте и входе; без env приложение по-прежнему работает гостем. Реальная облачная интеграция пока не подтверждена.

## Переключатели новых режимов (этап 14)

В `.env.example` добавлены `VITE_ENABLE_OPPOSITION` и `VITE_ENABLE_RING`. Точное значение `false` скрывает соответствующий режим и запрещает его запуск/возобновление; базовая программа остаётся доступной. Пустое значение сохраняет прежнее поведение (режим включён). История отключённого режима читается, прерванное занятие можно завершить с текущими результатами. Изменение требует новой сборки. До проверки камерой выставить оба значения `false` в Production; включать каждый режим отдельно после проверки.

Порядок выпуска и отката: [Release_PR.md](Release_PR.md). Результаты финального локального аудита: [Advanced_Stage_14_Report.md](Advanced_Stage_14_Report.md).

## Какие значения ещё нужны

1. Фактический стабильный **Production origin NeuroHand**, например адрес выбранного проекта Vercel; здесь он неизвестен, придумывать его нельзя.
2. **Supabase Project URL** из Connect, HTTPS без пути `/auth` или `/rest`.
3. **Supabase Publishable key** вида `sb_publishable_…`. Клиент намеренно не принимает secret-ключи и JWT-ключи старого формата.
4. Названия/идентификаторы выбранных проектов Supabase, Google Cloud и Vercel, чтобы не создать дубликаты в панелях.
5. Для Google нужны Client ID, callback URL из Supabase, реальные контактные сведения и адрес страницы о данных. Client Secret вводится непосредственно в панель Supabase; пароль БД, secret/service_role и пользовательские токены в чат или Git не передавать.

## Supabase и SQL Editor

1. Открыть `https://supabase.com/dashboard`. Если проект NeuroHand уже существует, использовать его. Иначе **New Project**, выбрать свою организацию, название `neurohand`, подходящий регион; пароль БД сохранить в менеджере паролей, не в приложении.
2. После готовности проекта открыть **Connect**, получить Project URL и Publishable key.
3. Открыть **SQL Editor → New query**, вставить весь `supabase/migrations/202609300001_training_sessions.sql`, выполнить один раз. Если таблица уже существует или запрос упал, не удалять таблицу и не запускать урезанный вариант: сначала сопоставить фактическую схему с миграцией.
4. В Table Editor проверить `public.training_sessions`, включённую RLS и две политики: SELECT своего `user_id`, INSERT с проверкой своего `user_id`. UPDATE/DELETE/anon не разрешены. Проверять доступ через обычные роли, а не только через привилегированный SQL Editor. [RLS Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)

Одна строка соответствует одному финальному занятию v3, `status` — `completed` или `stopped`. Составной первичный ключ `(user_id, id)`, FK на `auth.users`, индекс `(user_id, ended_at desc, id)`. `user_id` — UUID; `id` занятия — строка 1–200 символов: фактический локальный валидатор допускает строковые исторические id, новые занятия используют UUID. Переписывать старые id не нужно.

Payload ограничен 512 KiB, объектом разрешённых верхних полей, согласованностью id/схемы/дат/статуса/протокола с колонками, финальным состоянием без активной попытки. Явные ключи сырого трекинга запрещены рекурсивно. Полная проверка метрик упражнения остаётся в `parseSession`; SQL не повторяет распознавание. Legacy `attempts: null` допустимы как неизвестные попытки. RLS включена и принудительна; отладочного отключения политик нет.

## Google OAuth

1. Открыть `https://console.cloud.google.com`, выбрать или создать нужный проект.
2. В **Google Auth Platform** настроить **Branding**, **Audience**, **Data Access**. Указать настоящее название, контакт и доступную страницу о данных; для внешнего теста выбрать внешнюю аудиторию. В режиме Testing добавить оба тестовых Google-аккаунта в Test users.
3. Запрашивать только идентификацию (`openid`, `email`, `profile`). Drive, календарь и контакты не нужны.
4. В **Clients → Create client → Web application** создать OAuth-клиент. Authorized JavaScript origins — стабильный Production origin сайта без пути.
5. В Supabase **Authentication → Sign In / Providers → Google** скопировать callback URL проекта. Этот адрес, обычно `https://PROJECT_REF.supabase.co/auth/v1/callback`, вставить в Google **Authorized redirect URIs**.
6. В Google получить Client ID и Client Secret; внести их прямо в настройки провайдера Google в Supabase и включить провайдер. Secret не попадает в VITE-переменные.
7. Если Google требует публикации/проверки бренда, выполнить её до обещания публичного входа. Проверить второй обычный Google-аккаунт, а не только владельца проекта. [Инструкция Supabase для Google](https://supabase.com/docs/guides/auth/social-login/auth-google)

## Site URL и возврат

В Supabase **Authentication → URL Configuration**:

- Site URL: фактический стабильный Production URL NeuroHand.
- Redirect URLs: точный `https://ВАШ_PRODUCTION_HOST/` с завершающим `/`.
- Код использует `new URL('/', location.origin).href`. Никакого отдельного `/auth/callback` маршрута и нового Vercel rewrite не требуется.

Google возвращает пользователя на callback **Supabase**; Supabase возвращает на корень **NeuroHand**. Не менять эти адреса местами. Не добавлять широкие production-маски ради случайных Preview-развёртываний. Для отдельной тестовой среды/localhost разрешить только заранее выбранный точный адрес в соответствующем тестовом проекте. [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)

Выбран только **PKCE**: `flowType: 'pkce'`, `detectSessionInUrl: false`. Приложение однократно извлекает `code`, удаляет его из адресной строки **до** ожидания ответа и вызывает `exchangeCodeForSession(code)`. Повторный запуск и обычный reload не обменивают тот же callback ещё раз. После ошибки нужно заново войти. Токены и verifier хранит только SDK; собственной token-таблицы/localStorage-адаптера Auth нет. [PKCE Supabase](https://supabase.com/docs/guides/auth/sessions/pkce-flow)

## Локальные env и Vercel

1. Скопировать `.env.example` в `.env.local`, заполнить только:

   ```dotenv
   VITE_SUPABASE_URL=https://PROJECT_REF.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ
   ```

   Это обозначения, не реальные значения. `.env.local`, `.env.production` и другие `.env.*` исключены из Git; только пустой `.env.example` включён. Проверка: `git check-ignore .env.local`.
2. В Vercel открыть нужный **Project → Settings → Environment Variables**. Добавить эти две переменные в Production. Для Preview оставлять гостевой режим, пока отдельно не согласован и не разрешён стабильный тестовый адрес.
3. Настройки сборки остаются: Root Directory — корень репозитория, Framework — Vite, Build — `npm run build`, Output — `dist`. Production-ветка по плану — `main`; фактическая настройка панели не проверена. Рабочий этап сейчас только в локальной feature-ветке: redeploy старого main сам по себе не добавит этот код.
4. После доставки принятой версии в нужную ветку выполнить новое развёртывание. VITE-переменные встраиваются при сборке; существующий bundle не изменится от редактирования env. [Environment variables Vercel](https://vercel.com/docs/environment-variables)

## Изоляция и очередь

Прежние ключи `neurohand:progress:v3`, v2 и legacy принадлежат **гостю**. Для аккаунта ключи имеют префикс `neurohand:profile:user:USER_UUID:`. Первая авторизация ничего не импортирует из гостя; возвращение в гостевой режим возвращает его локальные данные.

При смене аккаунта текущая попытка закрывается по правилам паузы и занятие сохраняется **под прежним владельцем**. Камера останавливается; прежние результаты, история и canvas очищаются. При возвращении в тот же профиль можно продолжить его занятие после готовности. Данные, оставшиеся только в памяти из-за quota, также разделены между профилями. Пока Auth восстанавливается, персональные экраны скрыты.

Поколение профиля меняется при переключении, в том числе A → B → A; поздний ответ с прежним ticket отклоняется. Событие refresh чужой прежней сессии не меняет текущий профиль. Поздний ответ первоначального `getSession` не заменяет более новое событие Auth. При ошибке выхода старый профиль остаётся скрытым; доступно повторение выхода через SDK.

Очередь — восстанавливаемое представление финальных снимков конкретного пользовательского хранилища, с фиксированными owner/id/payload. Итог сохраняется локально до отправки. Метаданные подтверждения и повторов находятся в том же JSON-конверте; гостевая очередь пуста. Смена профиля прерывает запросы и отменяет таймеры, поздние ответы проверяются по владельцу и поколению.

Отправитель выполняет только INSERT одного занятия. Ответ сервера сверяется с полным итогом; при уникальном конфликте выполняется SELECT своего id и сравнение содержимого. Различающиеся итоги остаются конфликтом, без UPDATE и ложного подтверждения. Повторные временные ошибки получают задержку 2–60 секунд, запрос ограничен 15 секундами. Постоянная ошибка видна пользователю; после исправления можно нажать повтор. История загружается страницами по 30 строк, по ended_at убыванию и id возрастанию, объединяется с локальной по владельцу/id. Лимит видимых строк ничего не удаляет.

Статусы занятия: «В этом браузере», «Ожидает синхронизации», «Сохранено в аккаунте». Последний появляется только после проверенного серверного ответа. При отказе localStorage показывается предупреждение о хранении только в памяти: неподтверждённые данные могут пропасть после reload. Подтверждённые итоги можно заново загрузить из аккаунта.

Импорт гостевых занятий в аккаунт выполняется только после выбора записей и явного подтверждения; флажки изначально сняты. Повторный выбор не создаёт новые id. JSON-экспорт/импорт агрегатов — отдельный перенос между origin: до 5 MiB и 1000 финальных занятий, полная проверка до изменения истории, без токенов, облачных подтверждений и сырых данных камеры. Файл импортируется только в гостевой профиль; последующая загрузка в аккаунт требует отдельного выбора. localStorage с localhost автоматически на публичный домен не переезжает.

Подробности локальной проверки и сценарии второго устройства: [отчёт этапа 13](Advanced_Stage_13_Report.md).

## Проверки RLS двумя пользователями

Сначала выполнить реальный вход двумя тестовыми Google-аккаунтами и взять их разные UUID из Supabase Authentication → Users.

**Транзакционная проверка ролей:** в SQL Editor открыть `supabase/tests/rls_owner_checks.sql`, заменить только два UUID-плейсхолдера. Скрипт переключает выполнение на `authenticated` с claims A/B и `anon`, проверяет разрешения и заканчивает `rollback`. Он проверяет собственные SELECT/INSERT, отсутствие чужих строк, запрет чужого INSERT, UPDATE/DELETE, гостевого доступа, дубликатов и невалидных payload. Любое неожиданное разрешение вызывает исключение. Если выполнение остановилось с ошибкой, завершить тестовую транзакцию `rollback`, исправить причину, не выключать RLS.

**Реальный HTTP API:** `scripts/check-rls.mjs` использует два обычных access token от успешно вошедших тестовых пользователей. Это проверка JWT через Auth и PostgREST, которой не заменяет SQL impersonation. Перед запуском задать в окружении процесса `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `RLS_USER_A_ACCESS_TOKEN`, `RLS_USER_B_ACCESS_TOKEN`. Токены брать только из собственных тестовых сессий; не присылать их в чат, не сохранять в Git и не вставлять буквальные значения в shell history. Node не читает `.env.local` автоматически.

```sh
node scripts/check-rls.mjs
```

Этот отдельный live-тест **создаёт две синтетические остановленные сессии** `rls-check-…`, по одной в каждом тестовом аккаунте. Он не удаляет их, поскольку DELETE запрещён. Использовать тестовые аккаунты/проект. Скрипт не выводит токены, UUID пользователей или содержимое строк. Service role не нужен и не допускается как способ обхода тестов.

## Проверено локально и что осталось

- `npm test`: 185 тестов в 19 файлах; прежние упражнения проходят. Проверены отсутствие env, PKCE ровно один раз, отказ входа, stale bootstrap/refresh, выход с ошибкой, профили guest/A/B, очередь после reload, quota и реальные обработчики смены аккаунта с имитацией SDK/DOM.
- `npm run build`: production TypeScript/Vite успешно. SDK установлен без изменения стека.
- SQL миграция и весь `rls_owner_checks.sql` реально выполнены локально в PGlite с обычными ролями A/B/anon, имитированными `auth.users` и `auth.uid()`. Все проверки прошли; после rollback строк не осталось. Временный инструмент установлен вне репозитория и не добавлен в зависимости приложения.
- Это **не** проверка размещённого Supabase, настоящих JWT Google, HTTP API или опубликованного сайта. Live-скрипт подготовлен, но не запускался. В панелях изменений не выполнено: браузер не подключён, значения проектов неизвестны.

До признания внешней интеграции рабочей выполнить раздел 8 в панелях и подтвердить следующие шесть ручных сценариев:

1. Без env: базовое занятие и история работают гостем; сетевого Auth-запроса нет.
2. Реальный Google вход A: возврат в `/`, `code` исчезает, reload не повторяет обмен, гостевая история не появляется у A.
3. Сохранить занятие A, выйти и войти B: история/текущая попытка A скрыты; у гостя остаётся его собственная история.
4. Переключить пользователя во время упражнения: камера останавливается, прежнее занятие остаётся на паузе у прежнего владельца. При возврате A продолжение требует подготовки.
5. Отменить Google вход и проверить недоступность сети/ошибку выхода: нет ложного «Сохранено в аккаунте», локальные упражнения доступны после завершения обработки ошибки; выход с ошибкой оставляет прежний профиль скрытым.
6. Выполнить RLS SQL и live HTTP проверки двумя обычными аккаунтами, затем проверить публичный адрес в отдельном браузерном профиле. Затем выполнить сценарий синхронизации на втором устройстве из отчёта этапа 13.
