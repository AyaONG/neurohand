## 1. От чего отталкиваемся

Этот документ — план изменений, а не отчёт о проверенном коде. Изучены два скриншота, переписка с Gemini и документы NeuroHand_Build_Guide.md, NeuroHand_Runbook.md, NeuroHand_Step1_Detailed.md. Исходники текущей версии здесь не запускались. Codex должен проверить их в вашей папке проекта.

На первом скриншоте видны WRONG_FINGER, красный сустав и конкретная подсказка. На втором — «Пинцет: 5», CONFIRMED и отсутствие ошибки, но остаётся общая инструкция. Это показывает, что интерфейс отображает распознанные состояния; отдельный снимок не доказывает корректность всей последовательности повторений. Неработающие «Итоги» — наблюдение пользователя, причину нужно найти в коде.

Сейчас важнее всего исправить две вещи:

1. Человек не понимает, засчитано ли движение и сколько осталось до окончания.
2. У сессии нет видимого завершения и доступной истории, поэтому результат действий теряется для пользователя.

Добавление большого каталога упражнений не исправит эти проблемы. Сначала делаем три разные, законченные задачи и достоверную историю их выполнения.

### Что из старых документов больше не выполнять

| Старое указание | Новое решение |
|---|---|
| Создать проект и очистить main.ts | Проект уже работает. Ничего не создавать заново и не очищать |
| Искать проект на Desktop | По переписке он находится в `~/neurohand`; Codex проверяет фактический корень |
| Держать результаты только последней сессии | Хранить текущую сессию и историю отдельных сессий |
| Убрать третье упражнение при нехватке времени | Сохранить все три: это обязательный минимум регламента |
| Убрать тест на второй руке первым | Убирать сначала декор, дополнительные графики, звук и дополнительные режимы |
| Добиться ровно 18 тестов | Проверять конкретные свойства; количество тестов может изменяться |
| Переснять фикстуры и поменять ожидания, чтобы тесты прошли | Сохранять реальные контрпримеры; менять ожидания только после проверки неверной разметки |
| Любое исключение запрещено | Ожидаемая потеря руки обрабатывается обычным состоянием; ошибки камеры и хранилища требуют обработки |
| Выключить проверки TypeScript ради сборки | Точечно исправлять новые ошибки, например через `import type`; не менять настройки проекта без причины |
| `git checkout -- файл` как обычное исправление | Не уничтожать текущую работу. Исправлять конкретный дефект; откат — только с пониманием, что будет потеряно |
| «Отправки данных нет, потому что нет fetch» | Проверить реальные сетевые запросы; загрузка модели допустима, отправки видеокадров быть не должно |

Работающие камера, модель, геометрия и пороги остаются основой. Менять их следует при воспроизводимом дефекте, а не ради новой архитектуры. Расширять типы сессии и интерфейса разрешено; старое требование «types.ts никогда не менять» не должно блокировать эти согласованные изменения.

## 2. Как пользоваться планом на Mac

1. Скачай этот файл.
2. Открой существующую папку `neurohand` в VS Code: File → Open Folder. По переписке это домашняя папка → neurohand.
3. Внутри проекта открой папку `docs`. Положи туда файл под именем `NeuroHand_Upgrade_Plan.md`. Можно перетащить файл из Finder в папку `docs` в проводнике VS Code. Если папки нет — создать её через New Folder.
4. Открой чат Codex именно для этого проекта. Дай ему вводный промпт из раздела 13, затем промпт этапа 0–1.
5. После выполнения проверь указанное поведение в браузере. Затем давай следующий промпт. Не вставляй весь старый ранбук повторно.

Блоки с надписью «В чат Codex» вставляются в чат, не в терминал. Блоки `bash` — команды для терминала. Код TypeScript в этом файле описывает контракт для Codex: вручную переносить его по файлам не нужно.

Если нужны команды проверки, вводи во второй вкладке терминала:

```bash
cd ~/neurohand
pwd
git status --short
npm test
npm run build
```

Если `cd` не сработал — остановись и открой фактическую папку проекта; остальные команды нельзя выполнять вслепую в домашней папке. Не нужно заново запускать `git init`, `npm create vite` или добавлять origin.

Для браузера достаточно одного работающего `npm run dev`. Открывай адрес, который он вывел. Control + C останавливает этот сервер на Mac. Command + C копирует текст. Не используй `killall node` для обычного перезапуска.

## 3. Каким должен стать продукт

Главный сценарий: открытие → понятная цель → камера → подготовка руки → три задания → итоги → запись в истории.

Позиционирование в интерфейсе: «Три задания для движений кисти с подсказками по выполнению». Это прототип тренажёра; клинический эффект не измерен. История показывает выполнение заданий, а не восстановление здоровья.

### Карта экранов

| Экран | Что видит человек | Как заканчивается |
|---|---|---|
| Главная | Кнопка «Начать тренировку», три задания, «Мой прогресс», короткая инструкция | Начать и разрешить камеру |
| Подготовка | «Покажи ладонь целиком», рамка для руки, видимый прогресс калибровки | Валидная подготовка и короткий отсчёт |
| Тренировка | Название действия, цель, текущий результат, сцена, одна подсказка | Заданное число успешных действий |
| Переход | «Задание завершено. Следующее: …», короткая инструкция | Автоматический переход после готовности руки |
| Итоги | Результаты трёх заданий, завершённость, время, подсказки | История или новая тренировка |
| Мой прогресс | Предыдущие сессии, календарь активности за 7 дней, детали | Открыть запись или начать тренировку |

Разрешение браузера на камеру пользователь даёт сам. После этого полный основной сценарий, включая переходы и появление итогов, должен проходиться движениями без обязательных кликов по вкладкам. Кнопки паузы и завершения сохраняются как доступный дополнительный способ управления.

До старта предложить выбор «Левая рука / Правая рука». Если выбор пропущен, сохранить `unspecified` и не строить автоматическое сравнение разных сессий. В рамках одной тренировки просить пользоваться одной выбранной рукой. Базовая история рассчитана на одного человека в этом браузере; напарник для независимого теста использует свой браузер или устройство. Полноценные профили пользователей — отдельное последующее расширение.

### Компоновка тренировки

На широком экране: слева карточка задания, в центре камера с игровым объектом, справа прогресс трёх этапов. На узком экране карточки располагаются вертикально. Над камерой: «Задание 1 из 3». Крупный счёт: «3 / 5». Под камерой: одна актуальная подсказка. Все три блока могут быть обычными HTML-элементами; canvas нужен для сцены и скелета.

Не обязательно сохранять именно три колонки: на небольшом MacBook приоритет у камеры и читаемого задания. Не растягивать видеокадр для заполнения карточки. Слои видео, скелета и целей должны пользоваться одним преобразованием координат.

## 4. Три задания с понятной целью

Это игровые задачи для демонстрации управления рукой. Числа ниже — настройки прототипа, не рекомендованная нагрузка для пациента. Сначала реализуется один фиксированный набор `guided-v1`; дополнительные уровни откладываются.

| Технический режим | Название для человека | Действие | Результат | Цель сессии |
|---|---|---|---|---|
| pinch | «Собери 5 огоньков» | Развести большой и указательный, затем соединить | Один огонёк перемещается в коллекцию | 5 захватов |
| grip | «Сожми мягкий мяч» | Раскрыть кисть, затем сжать пальцы | Мяч сжимается, заполняется очередной сегмент | 5 сжатий |
| hold | «Проведи свет в цель» | Открытой ладонью довести указатель до круга и удержать | Заполняется кольцо, загорается цель | 3 цели по 2 секунды |

### Пинцет

- Инструкция: «Соедини большой и указательный пальцы. Разведи их перед следующим захватом».
- Огонёк появляется у области пинцета и реагирует на жест. В базовой версии не требовать отдельного прицеливания: сначала используем уже работающий детектор.
- Счёт увеличивается один раз на подтверждённое соединение после раскрытия. Это захват; раскрытие нужно для следующего захвата.
- После успеха: зелёный скелет, значок ✓, «Захват засчитан · 3 из 5», короткое перемещение огонька в коллекцию.
- После сообщения успеха: «Разведи пальцы для следующего захвата».
- При неправильном пальце: «Соедини большой и указательный пальцы» и точечная красная подсветка. Не окрашивать весь интерфейс в тревожный красный.
- Удержание закрытого пинцета не создаёт новых огоньков и не повторяет анимацию успеха.

### Мягкий мяч

- Инструкция: «Раскрой кисть, затем сожми пальцы — мяч станет меньше».
- Размер мяча меняется непрерывно на основе уже имеющейся `gripOpenness`, с ограничением допустимых размеров.
- Успех: «Сжатие засчитано · 2 из 5» и заполнение одного сегмента. При дальнейшем удержании новые сегменты не появляются.
- Открытая ладонь в начале — подготовка, не ошибка.
- При уверенно распознанном неполном сжатии мизинца: «Согни мизинец вместе с остальными пальцами». Не предлагать сжимать сильнее через дискомфорт.
- Если калибровка не удалась, нельзя выдавать fallback за персональную калибровку: показывать возможность повторить. Уже существующий технический fallback можно сохранить для устойчивости кода, но не для ложного сообщения «Готово».

### Проведи свет в цель

- Указатель связан с центром открытой ладони. Человек видит, чем он управляет.
- Три заранее заданные цели в средней, достижимой области кадра. Не использовать случайные координаты у краёв.
- Пример координат в нормализованной видимой сцене: (0.35, 0.50), (0.65, 0.45), (0.50, 0.65). Радиус — около 0.12 короткой стороны сцены. Это стартовые значения для ручной проверки на ваших экранах.
- Внутри цели открытой ладонью: кольцо заполняется, текст «Удерживай · 1,2 / 2,0 с».
- Снаружи: «Перемести ладонь в круг». После начала удержания и выхода: «Верни ладонь в круг и начни удержание заново».
- Сжатая кисть в круге: «Раскрой ладонь, чтобы удерживать цель». Только положение в круге недостаточно.
- Нет руки или невалидный кадр: накопление удержания сразу прекращается; непрерывное удержание начинается заново после восстановления.
- Одна цель даёт ровно один результат. Она блокируется после выполнения; затем активируется другая цель. Неподвижная рука не должна повторно выполнять старую цель.

## 5. Обратная связь: единые правила

Два debug-блока на скриншоте — один в HTML, другой на canvas. Скрыть нужно оба. Нельзя просто спрятать `<pre>`, оставив HUD поверх видео.

По умолчанию debug выключен при каждом обычном открытии. Включение — через существующий режим разработчика или `?debug=1`; клавишу D можно оставить. Dump доступен там же. Обычному пользователю не нужны FPS, nd, curl, handSize, ARMED или CONFIRMED.

| Состояние | Сообщение | Обратная связь |
|---|---|---|
| Подготовка | «Покажи ладонь целиком» | Спокойная рамка, без ошибки техники |
| Готовность | Конкретное движение для текущего задания | Голубой скелет |
| Подтверждённая ошибка | Один совет, который можно выполнить сейчас | Красный сустав + текст |
| Новый успех | «Засчитано · N из M» | Зелёный скелет 500 мс, сообщение около 900 мс, значок ✓ |
| Нужен новый цикл | «Разведи пальцы» или «Раскрой кисть» | Спокойная подсказка |
| Потеря руки | «Рука не видна. Верни ладонь в кадр» | Нет начисления баллов; очистить старый скелет |
| Завершение этапа | «5 из 5. Задание завершено» | Полный индикатор, инструкция следующего этапа |

Время подсветки — стартовая UX-настройка. Её можно изменить после просмотра, без переписывания детектора.

Приоритет сообщений: ошибка камеры → потеря видимости → устойчивая ошибка движения → завершение этапа → недавний успех → следующая инструкция. Сообщение успеха нельзя перезаписывать общей инструкцией уже на следующем кадре. При новой ошибке или пропаже руки безопасность счёта важнее сохранения поздравления.

Успех запускается по событию нового засчитанного действия, а не по условию `error === null` и не на каждом кадре `phase === CONFIRMED`. Для совместимости с текущей FSM допустимо сравнивать прежний и новый `reps` и создавать событие только при увеличении. Все счётчики, анимации и статистика получают одно и то же событие.

Не добавлять конфликтующие цепочки `setTimeout`, которые после смены задания могут очистить чужую подсказку. Предпочтительно хранить `successUntil` и текущий статус в одном контроллере интерфейса.

Для доступности: текст вместе с цветом, крупные элементы управления, достаточный контраст. Ключевой статус — HTML с `aria-live="polite"`, обновляемый по событиям, а не 60 раз в секунду. Декоративные анимации учитывать через `prefers-reduced-motion`. Звук — необязательный и выключаемый, не единственный сигнал.

## 6. Итоги и прогресс: что считать

### Итоги одной сессии

Верхняя строка: «Тренировка завершена» только после всех трёх заданий. При досрочном выходе: «Тренировка остановлена. Сохранён выполненный объём».

Ниже: три карточки с выполнено / запланировано; активное время; эпизоды подсказок по каждому заданию. Для переноса — число целей и лучшее непрерывное удержание с ограничением значением цели, например 2,0 с.

Не показывать фиктивную оценку вроде 97% точности. Допустимо «Выполнено 3 из 3 заданий» — у этого показателя ясный смысл. Если упражнение ещё не начато, писать «Не начато», а не «Ошибок нет». Если начато, но действий не завершено — «0 из 5».

Открытие итогов во время тренировки должно показывать текущий снимок и ставить тренировку на паузу, не завершать и не обнулять её. Доступны «Продолжить» и «Завершить тренировку». После полного завершения открывается финальный неизменяемый результат.

### Мой прогресс

Обязательная версия до сдачи:

1. Последняя тренировка: дата, статус, выполненные задания.
2. Активность за последние 7 местных календарных дней: отметка в дни завершённых тренировок. Если была только частичная — отдельный нейтральный маркер.
3. История до 30 последних сессий: дата и время, выбранная рука, завершённость, пинцет / сжатия / цели, активное время. Ограничение «Последние 30 тренировок» указать в интерфейсе.
4. Открытие деталей любой записи без включения камеры.
5. Сравнение последних двух сопоставимых завершённых сессий: фактические значения рядом. При одной записи — «Заверши ещё одну тренировку с теми же настройками для сравнения».

Сопоставимость: одинаковые протокол, явно выбранная рука, цели упражнений, настройки удержания и версия распознавания. При неизвестной руке автоматическое сравнение отключено. При изменении порогов, режима или выбранной руки не утверждать, что разница означает улучшение. Практику и частичные сессии показывать отдельно от завершённой программы.

График последних сессий — второй приоритет после рабочей таблицы. Если есть время, нарисовать небольшую SVG-диаграмму количества выполненных действий по одному выбранному упражнению с подписью оси и доступной таблицей. Не выдумывать предыдущие данные ради красивой линии. При 0–1 сессии достаточно пустого состояния или одной точки.

### Определения метрик

| Поле | Как вычислять | Что исключать |
|---|---|---|
| Успешные действия | По одному событию подтверждения, с ограничением целью этапа | Кадры удержания уже засчитанного жеста |
| Эпизоды подсказок | Одна устойчивая ошибка как один эпизод | Дребезг меток, каждый видеокадр, отсутствие руки |
| Активное время | Интервалы активного задания при пригодном трекинге | Инструкции, калибровку, паузу, итоги, скрытую вкладку, потерю руки |
| Лучшее удержание | Максимальная непрерывная длительность внутри цели с открытой ладонью | Время без новых пригодных кадров |
| Завершённость | Все цели трёх этапов выполнены | Сам факт открытия кнопки «Итоги» |

Эпизод подсказки: начать после примерно 250 мс устойчивой конкретной ошибки; закончить после примерно 300 мс пригодных кадров без этой ошибки. Если ошибка сразу сменяется на другую, подтвердить новый код тем же правилом. Эти интервалы — параметры интерфейса и аналитики. Начисление успеха блокируется уже самим невалидным движением, а не только после ожидания подсказки.

Краткая потеря руки не должна превращать одну ошибку в десять эпизодов: не считать пропуск исправлением. После длинной паузы / смены этапа очистить текущее состояние эпизода без дополнительного начисления. Не смешивать этот механизм со старым тайм-аутом выбора ошибочного пальца.

## 7. Сессия и сохранение: контракт для Codex

Имена можно адаптировать к существующим исходникам. Это минимальная модель данных, не повод переписать работающие модули.

```ts
type SessionStatus = "in_progress" | "completed" | "stopped";
type ExerciseId = "pinch" | "grip" | "hold";

type ExerciseResult = {
  completed: number;
  target: number;
  started: boolean;
  activeMs: number;
  promptEpisodes: Record<string, number>;
  bestHoldMs: number | null;
};

type SessionRecord = {
  schemaVersion: 2;
  id: string;
  startedAt: string; // ISO-дата, календарное время
  endedAt: string | null;
  status: SessionStatus;
  mode: "guided" | "practice";
  hand: "left" | "right" | "unspecified";
  protocolId: string;
  recognitionVersion: string;
  settings: {
    pinchTarget: number;
    gripTarget: number;
    holdTargetCount: number;
    holdTargetMs: number;
    targetRadiusRatio: number;
  };
  currentExercise: ExerciseId;
  exercises: Record<ExerciseId, ExerciseResult>;
};
```

Времена коротких интервалов и удержания считать по монотонной шкале (`performance.now()`); даты записей — календарные. Не сохранять `performance.now()` как время начала сессии: после перезагрузки это другая шкала.

Предпочтительно хранить одну оболочку `neurohand:progress:v2` с `schemaVersion`, текущей сессией и массивом истории. При финализации переместить запись в историю и очистить текущую одним сохранением оболочки. Повторная финализация того же `id` не создаёт дубликат.

Сохранение: после подтверждённых действий, начала эпизода подсказки, перехода этапа, паузы и завершения; активное время периодически, например раз в 2 секунды. Не записывать localStorage на каждом видеокадре.

При перезагрузке обнаруженная текущая сессия показывается как прерванная. Предложить «Продолжить» или «Завершить». До продолжения заново подготовить руку и обнулить незавершённое удержание / промежуточную фазу жеста; уже засчитанные действия сохранить. Пока выбор не сделан, её нельзя автоматически считать завершённой.

`JSON.parse`, чтение и запись защищены от ошибок. При запрете хранилища тренировка продолжает работать в памяти; текст: «В этом браузере история не сохраняется. Итоги доступны до закрытия страницы». При повреждённой записи — не падать и не стирать молча всю историю. Валидировать структуру, конечность чисел и неотрицательность счётчиков.

Если есть старый ключ `neurohand-session`, проверить его схему. Доступные счётчики показывать как отдельную legacy-запись с пометкой старой версии; для неё использовать отдельный тип, допускающий неизвестные поля, а не заполнять обязательные поля SessionRecord выдуманными значениями. Старые записи не использовать для автоматического сравнения. Исходную запись сохранять до успешной миграции.

Сохранять только настройки, даты и агрегированные результаты. Видео, фотографии, массивы landmarks и медицинские сведения не нужны. Debug Dump остаётся отдельной явной функцией разработчика.

Важно для проверки: localStorage привязан к браузеру и origin, включая порт. История на `localhost:5173`, `localhost:5174`, `localhost:4173` и опубликованном сайте — разные хранилища. Это не ошибка сохранения. Между устройствами история в этой версии не синхронизируется. [1]

## 8. Управление тренировкой и временем

Существующая FSM распознаёт отдельный жест. Над ней нужен небольшой контроллер программы. Не превращать каждую надпись на экране в новую фазу геометрии.

Состояния программы: `intro`, `preparing`, `exercise`, `transition`, `paused`, `summary`. История — отдельный экран без работы счётчиков.

- Одно нажатие «Начать» запускает запрос камеры и подготовку.
- Подготовка: пригодная открытая ладонь, успешная калибровка и короткий видимый отсчёт. Кадры подготовки ничего не засчитывают.
- На 5-м захвате этап завершается один раз. В переходе новые жесты не начисляются.
- Переход показывает следующее задание примерно 3 секунды. Затем ждёт пригодную раскрытую ладонь, чтобы закрытый жест предыдущего этапа не стал первым результатом нового.
- После третьего задания сессия финализируется и итоги появляются автоматически.
- Потеря руки сразу останавливает счёт и накопление удержания. Сообщение можно задержать на 150–250 мс, чтобы не мигало; это не разрешает продолжать начисления.
- При длительной потере, например 2 секундах, — пауза с объяснением. Возврат требует готовой открытой ладони и короткого отсчёта; новых кликов для основного сценария не требуется.
- Ручная пауза и промежуточные итоги возобновляются отдельной кнопкой, чтобы пользователь сохранял контроль.
- Скрытая вкладка вызывает паузу. При возвращении не прибавлять весь пропущенный интервал к удержанию. Page Visibility API позволяет отслеживать это явно. [2]
- Длинный промежуток между новыми кадрами, например более 250 мс, считать разрывом наблюдения: не засчитывать его как удержание; переустановить временную базу и промежуточное состояние. Значение проверить на целевом ноутбуке.
- Начисления разрешены только в `exercise`; итоговый объект после завершения не меняется от руки перед камерой.
- Не создавать вторую цепочку `requestAnimationFrame` и второй трекер при повторном старте. При окончательном выходе выключить media tracks; повторный старт корректно возвращает камеру.

Стабилизация жестов должна учитывать реальные новые кадры, а не частоту перерисовки экрана. Если текущая FSM ещё считает кадры, менять её только в пределах этапа контроллера и проверять одно и то же поведение на последовательностях с разным шагом времени. Это не требует переделывать геометрию.

## 9. Предлагаемое распределение модулей

Это карта ответственности. При наличии аналогичных модулей расширять их, не создавать дубликаты ради названий.

| Модуль | Ответственность |
|---|---|
| `geometry.ts`, `validator.ts` | Существующие измерения и распознавание |
| `fsm.ts` | Одноразовое подтверждение жеста и удержание |
| `session.ts` | Единый объект результатов и обработка событий |
| `program.ts` | Порядок заданий, пауза, переходы, завершение |
| `feedback.ts` | Приоритет подсказок, длительность успеха |
| `results.ts` | Итоги из данных сессии |
| `storage.ts` | Чтение / запись / проверка сохранённых данных |
| `history.ts` | История, календарь и сопоставимые сессии |
| `draw.ts` | Скелет, мяч, огоньки, цели, кольцо |
| `main.ts` | Соединение камеры, контроллера и экранов |

Направление данных: кадр → распознавание → подтверждённое событие → сессия и программа → отображение. Отрисовка сама не увеличивает счёт. Итоги не собирают числа из DOM или отладочного текста.

Для исправления текущего дефекта допустимо временно формировать `REP_CONFIRMED` сравнением старого и нового счётчика FSM. У события должны быть идентификаторы текущих сессии, упражнения и действия, чтобы повторная обработка не создала второй результат. На смене упражнения промежуточная FSM сбрасывается, агрегированные результаты сессии сохраняются.

## 10. Очерёдность реализации

Оценки времени — рабочие ориентиры, не обещание скорости Codex. Если этап затягивается, сокращать декоративную часть и дополнительные режимы. Итоги, три задания, обратная связь, простая история и проверка запуска остаются.

| Этап | Что получаем | Ориентир | Зависимость |
|---|---|---|---|
| 0 | Проверенное понимание текущего кода и сохранённая исходная работа | 15–20 мин | — |
| 1 | Видимый успех, рабочие «Итоги», скрытые debug-панели | 40–60 мин | 0 |
| 2 | Программа из трёх заданий с автоматическим завершением | 60–90 мин | 1 |
| 3 | Три наглядные игровые сцены | 45–75 мин | 2 |
| 4 | Сохранение, история и простой трекер активности | 60–90 мин | 2; сцены могут быть уже готовы |
| 5 | Читаемый интерфейс и необходимые состояния ошибок | 30–45 мин | 1–4 |
| 6 | Проверка полной сессии, сборки и опубликованной версии | 60–90 мин | 1–5 |

Практический порядок для одного разработчика: 0 → 1 → 2 → 3 → 4 → 5 → 6. Не переключаться между несколькими ИИ-планами посреди этапа. Если полноценный новый модуль не нужен, Codex вправе объединить небольшие функции с существующим модулем и объяснить это в отчёте.

### Этап 0. Короткий аудит и точка возврата

Codex проверяет:

1. Фактический корень, ветку, `git status`, diff, существующие инструкции AGENTS.md.
2. Текущие `package.json`, `index.html`, `style.css`, `main.ts`, `fsm.ts`, `draw.ts`, `debug.ts`, `types.ts`; затем модули результатов / сессии, если они есть.
3. Где меняется `reps`, где рисуется зелёный цвет, кто задаёт `#hint`, кто обрабатывает `#btn-results`, почему секция результатов не становится видимой.
4. Где сохраняются счётчики и очищаются ли они при переключении вкладки.
5. Базовые тесты и сборку. Результат фиксируется честно; ошибки исходной версии отделяются от новых.

На скриншоте VS Code видны изменённые файлы, поэтому нельзя начинать со сброса или жёсткого переключения ветки. Сохранить относящуюся к проекту работу локальным checkpoint-коммитом после просмотра diff. Не включать секреты, node_modules и случайные файлы. Для обновления можно использовать ветку `feature/neurohand-product`; если она уже существует, проверить её, а не создавать ещё одну похожую.

Результат аудита — короткая таблица «симптом → причина в текущем коде → исправление». Аудит не должен превращаться в отдельную ночь рефакторинга.

### Этап 1. Исправить успех и «Итоги»

Порядок внутри этапа:

1. Найти и исправить связь кнопки с экраном. Проверить id, обработчик, раннее исключение, hidden / CSS и отсутствие данных. Не угадывать единственную причину по скриншоту.
2. Ввести или подключить единый объект сессии. Если он уже есть, расширить его. При переключении режимов общий результат не теряется.
3. Подключить одноразовое событие нового результата к сессии, зелёной подсветке и тексту успеха.
4. Сделать временные итоги для текущей сессии: три результата, пустое состояние, пауза и возврат.
5. Скрыть debug в HTML и на canvas; Dump перенести в режим разработчика.

Не нужно ждать красивых карточек, чтобы кнопка заработала. Первая версия итогов может быть простым HTML, который отображает настоящие данные.

Проверка руками:

- После открытия страницы нет отладочных чисел.
- Открыть итоги до первого движения: видна понятная пустая сессия, экран не пустой.
- Сделать три захвата: три отдельных сообщения, каждый результат засчитан один раз.
- Удерживать пинцет: новых сообщений успеха и баллов нет.
- Открыть итоги: «Пинцет: 3», остальные задания не начаты.
- Двигать рукой на экране итогов: цифры не меняются.
- Вернуться: результат остаётся, новый цикл начинается с раскрытия.

После этого этапа уже исправлены три непосредственные жалобы: «ничего не высвечивается», «цифры мешают», «итоги не открываются».

### Этап 2. Связать действия в тренировку

1. Добавить фиксированный протокол: 5 захватов, 5 сжатий, 3 цели по 2 секунды.
2. Реализовать подготовку с понятным статусом калибровки и стартом по готовности руки.
3. Добавить контроллер программы из раздела 8. Существующие детекторы используются через небольшой адаптер.
4. Ограничить счёт целью этапа. Один и тот же жест не должен завершить этап, перейти дальше и немедленно засчитаться снова.
5. Разделить промежуточные итоги и окончательное завершение.
6. После последней цели сформировать финальный результат ровно один раз. Новая тренировка получает новый id и нулевые счётчики; прежняя запись остаётся.
7. Обработать потерю руки и скрытую вкладку. После пропуска никаких начислений за невидимое время.

Проверка: после выдачи браузером разрешения пройти все три задания без кликов по вкладкам. Должны появиться итоговые 5 / 5, 5 / 5, 3 / 3. Не показывать «тренировка завершена», если выполнено только первое упражнение.

Здесь нужны содержательные тесты состояния: единственное начисление, переход после цели, невозможность счёта в паузе / итогах, отсутствие второго начисления после пропажи руки, финализация один раз. Не писать тесты, которые только повторяют имена CSS-классов.

### Этап 3. Добавить наглядные сцены

Реализовать раздел 4 на Canvas / SVG / CSS без тяжёлых игровых библиотек и без изменения распознаваемых жестов.

1. Пинцет: пять видимых мест в коллекции, один огонёк за подтверждённый захват. Анимация запускается событием, не запросом координат.
2. Сжатие: полупрозрачный мяч, который следует за раскрытием кисти; пять сегментов результата. Размер шара не является отдельной метрикой здоровья.
3. Перенос: видимый указатель ладони, цель и кольцо. Показать направление движения, когда указатель вне круга. Удержание проверяет и положение, и пригодность открытой ладони.
4. Согласовать зеркало, crop и масштаб. Если выбран `object-fit: cover`, учесть смещение и обрезку во всех слоях; более простой вариант — сцена с фактическим aspect ratio видео и одинаковым отображением слоёв.
5. Не размещать целью руку под непрозрачными панелями. Не уменьшать текст ради эффектов.

Проверка: на ноутбуке сразу видно, какой объект управляется рукой и что изменилось после действия. Для третьего задания вывести ладонь из цели перед заполнением: балла нет, кольцо обнулилось. Вернуть руку кулаком: удержание не продолжается.

### Этап 4. Сделать историю, которой можно доверять

1. Реализовать сохранение по схеме раздела 7. Начать с завершённой сессии, затем добавить восстановление прерванной.
2. Сделать экран «Мой прогресс» с пустым состоянием: «Здесь появятся твои тренировки».
3. Показать последние записи, их детали и 7-дневную активность. Даты группировать по локальной дате пользователя; для проверки в Казахстане — Asia/Almaty. Не использовать UTC-день через `toISOString().slice(0,10)` как локальный день.
4. Сравнить две записи только при совпадении условий. Показывать числа и контекст, а не оценку «здоровье улучшилось».
5. Повторное открытие итогов не добавляет запись. Перезагрузка во время тренировки не объявляет её завершённой.
6. Обработать недоступное и повреждённое хранилище. Не использовать `localStorage.clear()`, которое затронет чужие ключи этого origin.

Проверка руками на ОДНОМ адресе и в ОДНОМ браузере:

- Завершить сессию А; открыть историю — одна запись.
- Трижды открыть и закрыть итоги — по-прежнему одна запись.
- Завершить сессию Б — две отдельные записи.
- Обновить страницу — обе сохранились, их детали совпадают с итогами.
- Начать третью, выполнить пару действий и обновить — предложено продолжить прерванную, а не начать её с нуля молча.

Сравнение в первую очередь текстовое. График, экспорт CSV, удаление записей и дополнительные профили — после основного сохранения и чтения, если остаётся время.

### Этап 5. Привести интерфейс к одному стилю

Это точечная доработка, не новый дизайн с нуля.

1. Иерархия: цель → текущий шаг → выполнено / осталось → подсказка. Надписи состояния должны быть читаемы с расстояния, на котором рука попадает в кадр.
2. Карточки этапов: «Готово», «Сейчас», «Далее», а не три равноправные вкладки без порядка.
3. На главной кратко объяснить движение для каждого задания. Можно использовать простой CSS / SVG-пример: два пальца сходятся, мяч сжимается, точка идёт к кругу.
4. Убрать англоязычные технические статусы из обычного режима. Добавить видимые состояния загрузки модели, запрета камеры, отсутствия руки и ошибки сохранения.
5. Техническую загрузку камеры и модели не называть калибровкой руки.
6. Кнопки «Пауза», «Итоги», «Мой прогресс» должны отвечать на действие и иметь понятное активное состояние. При открытии истории из тренировки — пауза с сохранением текущего результата.
7. Мобильная адаптация по ширине, отсутствие горизонтального скролла. Полноценную поддержку всех мобильных камер не обещать без проверки.

Небольшой текст в настройках / информации: «Прототип тренажёра. Результаты описывают выполнение заданий». Краткое предложение про комфортное движение уместно на старте, но не нужно закрывать каждую сцену предупреждениями.

### Этап 6. Проверить и подготовить сдачу

1. Запустить автоматические проверки, которые реально есть в `package.json`, и `npm run build`.
2. Открыть собранную версию через существующий `npm run preview`; если скрипта нет — локальный `npx vite preview`. Адрес берётся из вывода терминала.
3. Проверить модель / WASM, камеру, все три задания, итоги и историю. HTTP 200 у модели сам по себе не подтверждает работу распознавания.
4. Проверить опубликованную HTTPS-версию без входа в аккаунт хостинга. Камера требует подходящего защищённого контекста; localhost поддерживается для разработки. [3]
5. Напарник проходит сценарий сам, без подсказок разработчика. Записать конкретные затруднения и исправить критические.
6. Проверить README: фактические команды, версии окружения из проекта, три жеста, режим ошибки, история, ограничения локального сохранения, реально проверенные устройства.
7. Проверить публичный GitHub и наличие последнего нужного коммита. Не переписывать историю ради даты старта.
8. Записать демонстрацию 60–120 секунд: цель задания → правильное движение → конкретная ошибка → исправление → три задания → итоги → запись в истории. Продолжительность — рабочий формат ролика, не заявленный обязательный пункт регламента.

В приложении не должно быть автоматического успеха по таймеру для красивого демо. Для проверки можно использовать отдельные явно помеченные тестовые данные, но не сохранять их как реальные тренировки.

30 сентября с 12:00 не добавлять новые режимы и графики; к 13:00 закончить проверку версии для сдачи; к 14:00 отправить форму. Между 14:00 и официальными 15:00 оставить резерв на доступ к ссылкам и организационные проблемы.

## 14. Как сообщать Codex об обнаруженной ошибке

Указывать действия и ожидаемый результат. Пример:


Для итогов: точное количество сделанных действий, что показывает счёт во время задания и что показывает экран итогов. Для истории: браузер, полный адрес с портом, что было до перезагрузки и после неё. Для дрожания: короткая запись, а не только одиночный скриншот.

## 15. Основания технических решений

Исходные материалы: три приложенных документа, два скриншота, переписка и приведённый в ней регламент. Требования UX, значения задержек и объём заданий в этом документе — предложенная спецификация прототипа, подлежащая ручной проверке; они не являются клиническими нормативами.

Официальные технические справочники, проверенные при подготовке:

1. [MDN: localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) — хранение в пределах origin, сохранение между сеансами браузера и возможные ограничения доступа.
2. [MDN: Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) — отслеживание скрытой вкладки и пауза приложения.
3. [MDN: getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) — запрос камеры и защищённый контекст.

Начать следует с запроса 0–1. Его результат должен быть виден сразу: чистый экран, понятное подтверждение движения и работающие итоги текущей сессии.
