# Корректирующая работа после этапов 7–14

База: 266973e, feature/neurohand-attempts; исходное рабочее дерево чистое.

## Вход и интерфейс

Причина отсутствия входа подтверждена в ~/neurohand: существует только пустой .env.example, .env.local нет. cloudConfig читает VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY из import.meta.env; при отсутствии обоих клиент не создаётся, кнопка скрыта. Vite загружает .env.local при запуске/сборке, файл-шаблон .env.example не загружает. Не создавались вымышленные URL/ключи.

Обнаружен процесс Node с cwd ~/neurohand, слушающий 127.0.0.1:5173. Для запуска по этому адресу точный возврат — http://127.0.0.1:5173/. Если открыть через localhost, фактический callback будет http://localhost:5173/: origin различается. Production origin неизвестен.

Нужно: получить Project URL и Publishable key в выбранном Supabase, локально заполнить две VITE-переменные в .env.local, перезапустить dev-сервер. В Authentication → Providers включить Google и внести OAuth Client ID/Secret из Google; в Google Authorized redirect URIs внести callback из панели Supabase (не адрес NeuroHand). В Supabase URL Configuration разрешить точный http://127.0.0.1:5173/ для локального теста. Для production указать фактический HTTPS origin и корень / в Site URL/Redirect URLs. RLS не отключать. Значений проекта и доступа к панелям пока нет; успешного внешнего входа не было.

Кнопка «Войти» использует Supabase Google PKCE; code удаляется из URL перед однократным обменом SDK. Ошибки по-прежнему не раскрывают произвольные сообщения провайдера, но безопасные категории provider/callback/network доступны в ?debug=1. Обычный текст объясняет недоступность входа без терминов конфигурации. Гостевая подпись — «Прогресс сохраняется в этом браузере»; предупреждение отказа хранилища остаётся отдельно.

«Скачать историю» / «Загрузить историю» находятся в «Настройках». Нормированные расстояния и причины в кодах доступны только в debug; убрана дублирующая сводка попыток.

## Прохождения, цели и попытки

Новые занятия хранят attempts.runs: exerciseRunId и упорядоченные goalIds. Каждая новая попытка ссылается на них и имеет attemptOrder. У старых снимков этих полей по-прежнему нет: валидатор читает прежнюю схему без догадок, финальные payload не переписываются. Новая семантика выделена в ключе сопоставимости истории как goals-v1; старые и новые серии не сравниваются как одинаковые. Расширение вложенного attempts совместимо с разрешённым JSON существующей SQL-миграции, RLS не меняется.

Раньше consumesPair потреблял слот при partial/incomplete, а кольцо завершало занятие после неполного круга. В новых прохождениях цель закрывается успехом или явным пропуском; после неполной попытки остаётся прежняя цель. Вернуться в исходную позу нужно до нового движения. Пользователь по-прежнему может завершить всё занятие с частичными итогами.

Раньше ошибка WRONG_FINGER запрещала начало попытки в режиме пар. Теперь после готовности устойчивое движение неправильной пары может начать одну попытку, но не успех. Возврат закрывает её, удержание не создаёт серию. Потеря руки даёт unscorable и исключается из числа оценённых попыток до успеха.

0,3 с не подтверждены камерой: скриншоты в задаче не приложены. В прежнем детекторе резкое сближение давало примерно intentMs 150 + confirmMs 180. Медленное движение должно учитываться с порога намерения; тестирует длительность больше секунды. В базовом наблюдателе убрано повторное требование ARMED после уже установленной готовности (сжатие переводит FSM в подтверждение), у кольца включено пригодное время окна намерения. Паузы и разрывы отслеживания не добавляются.

Проверен сценарий двух неправильных возвратов и успеха: один goalId, attemptOrder 1/2/3, одна выполненная цель, сообщение «Выполнено с третьей попытки», сохранение после reload. Дополнительно проверены unscorable перед успехом, пропуск без успеха и отклонение чужой ссылки goalId.

## Произвольные пары

Каталог PAIR_CATALOG содержит 10 уникальных пар, каждая задана tips:[id,id]. Прежние числовые ключи thumb-пар сохранены для совместимости; новые попытки дополнительно хранят два target-кончика, версию правил и агрегат исходного расстояния наблюдаемого движения. Шесть нетипичных пар доступны только через снятые флажки «Экспериментальные пары без большого пальца», в базовую программу не добавлены.

Для них используется отдельная версия free-pairs-v1: свой диапазон исходной позы, порог движения, 300 мс подтверждения, отдельные пороги сближения/раскрытия. Проверяются наблюдаемое движение после готовности, перекрытие кончиков, третий близкий кончик и большое различие оценённой MediaPipe глубины. Это консервативные экспериментальные признаки видимости, не измерение физического касания. Произвольно согнутые посторонние пальцы вне зоны выбранной пары не запрещены. Пороги базового readPinch не менялись.

Неправильное движение определяется относительно исходных расстояний; оно учитывается одной попыткой. После таймаута необходимо раскрыть именно двигавшуюся пару, иначе удержание не создаёт новых попыток. Выделение на рисунке/видео, подсказки, итоги, фильтр сопоставимости, валидатор JSON и история поддерживают обе выбранные точки.

## Фактические проверки и оставшиеся действия

Дополнительно запрос к работающему Vite http://127.0.0.1:5173/src/main.ts подтвердил отсутствие/пустоту обоих Supabase env в реально отдаваемом модуле; значения не выводились. Поэтому успешный внешний вход здесь пока невозможен без публичных настроек проекта. Запрос этих значений пользователю отправлен; отсутствие внешнего доступа не остановило остальные части.

Локально проходят 206 тестов / 20 файлов и production-сборка. Проверены две наблюдаемые неполные целевые попытки → успех, отдельно две неправильные пары → успех, отображение третьей попытки через настоящие обработчики приложения с имитацией DOM, сохранение/восстановление после reload, unscorable вне счёта до успеха, пропуск, удержание и повтор, шесть новых пар на зеркальных синтетических данных, гостевые данные и изоляция A/B с имитацией SDK. git diff --check проходит.

Настоящая камера, успешный Google-вход, размещённая RLS с двумя обычными аккаунтами и синхронизация на втором устройстве **не проверены**. Новую SQL-миграцию эта корректировка не требует: новые поля находятся внутри разрешённого JSON attempts/opposition; правила доступа не изменены. Предыдущий frontend не понимает новые связи и пары — не откатывать на него без экспорта истории и проверки совместимости. История v3 текущей версии и прежние финальные снимки в новом frontend читаются.

Ручная проверка:
1. Заполнить публичные env, перезапустить Vite, разрешить указанный точный callback; проверить «Войти», реальный Google-возврат и reload. Затем A → B: чужие занятия и очередь не появляются.
2. Гостем выбрать одну thumb-пару. Дважды начать небольшое сближение и вернуться, затем выполнить полностью: одна цель, три оценённые попытки, «Выполнено с третьей попытки». Открыть итоги и перезагрузить.
3. Удержать успешную пару 3 секунды, раскрыть; балл один, следующая цель только после раскрытия. После partial повторяется прежняя пара; «Пропустить» не даёт успех.
4. Во время движения убрать руку/скрыть вкладку: unscorable без человеческой неудачи, время отсутствия не добавляется. Сравнить быстрое и медленное движение — длительность зависит от наблюдаемой попытки.
5. Вручную выбрать удобную пару без большого пальца. Проверить обе руки, исходное раскрытие, неполное/полное сближение, перекрытие и подсветку ровно двух кончиков; неудобные пары снять.
6. В настройках скачать историю, загрузить её гостем в другом браузере; повторный импорт без копий. После настоящего входа выбрать импорт в аккаунт явно и проверить историю на втором устройстве.
