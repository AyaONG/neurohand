# Этап 13 — сохранение и синхронизация результатов

База: локальный коммит этапа 12 `4aa6de2`, ветка `feature/neurohand-attempts`. Этапы 0–1 не повторялись. Распознавание, модель MediaPipe и пороги упражнений не менялись. Публикация и изменения внешних панелей не выполнялись.

## Поведение

- Финальное занятие сначала сохраняется локально с прежним единственным sessionId. Очередь и сведения о подтверждении находятся в конверте Progress v3 конкретного владельца. Необязательное поле sync не изменяет Session v3 и не придумывает попытки legacy-записям.
- Облако получает один неизменяемый итог через INSERT. Успешный ответ проверяется по владельцу, колонкам и полному payload. При конфликте уникальности выполняется SELECT своего id: только одинаковое содержимое подтверждает сохранение. Различие не перезаписывает ни одну сторону.
- Временные ошибки повторяются через 2, 4, 8… секунд, максимум 60 секунд. Срок сетевого запроса — 15 секунд. Задержка и число ошибок переживают reload. Постоянные ошибки видны и требуют исправления причины и явного повтора.
- История загружается страницами по 30 строк с курсором ended_at DESC / id ASC. Локальная история объединяется по владельцу/id, включая несинхронизированные итоги. Число видимых строк не является лимитом хранения.
- Owner и поколение фиксируются до ожидания сети. Смена аккаунта прерывает запросы и таймеры; запоздавшие ответы A не меняют данные и экран B, включая A → B → A.
- Статусы: «В этом браузере», «Ожидает синхронизации», «Сохранено в аккаунте». Вход сам по себе не означает сохранение. При quota/запрете localStorage явно указано хранение только в памяти: неподтверждённые данные не переживут reload. Подтверждённые данные восстанавливаются загрузкой из аккаунта.
- Гостевые занятия импортируются только после выбора снятых по умолчанию флажков. Исходные записи остаются гостю; id сохраняются, повторный импорт не дублирует занятия.
- JSON-перенос агрегатов отдельно от облака: до 5 MiB и 1000 финальных занятий, проверка всего файла и конфликтов до изменения истории. Только гостевой профиль принимает файл; загрузка выбранных записей в аккаунт — отдельное действие. Нет токенов, видео, траекторий или landmarks. Автоматического переноса localStorage с localhost на другой origin нет.

Основные файлы: `src/sync.ts`, `src/storage.ts`, `src/profiles.ts`, `src/session-equality.ts`, `src/transfer.ts`; UI — `src/main.ts`, `src/history.ts`, `src/results.ts`, `index.html`. Используется миграция этапа 12 без дополнительных прав UPDATE/DELETE и без отключения RLS.

## Проверено локально

`npm test`: **185 тестов / 19 файлов**. `npm run build`: TypeScript и production Vite проходят. `git diff --check`: проходит.

Новые тесты проверяют потерянный ответ после успешного серверного INSERT и повтор после reload; совпадающий и несовпадающий конфликт id; постоянный отказ доступа; офлайн и восстановление связи; задержки; поздние INSERT/SELECT аккаунта A; страницы с одинаковым временем и объединение без потери локальных строк; чужие/невалидные ответы; quota; выбранный импорт гостя и повтор; проверку JSON. Тест транспортного слоя использует установленный Supabase SDK с имитацией fetch и проверяет запросы, фильтр владельца, курсор с особенными символами и таймаут. UI-тест проверяет явный выбор гостевых занятий и подтверждённый статус.

Это локальные проверки с имитацией транспорта/DOM. Реальный Supabase, Google OAuth, JWT/RLS через HTTP, публичный сайт и второе устройство **не проверены**. Публичные значения выбранного проекта и Production URL не предоставлены; ранее доступный инструмент не обнаружил подключённого браузера. Настройка и проверки двух обычных пользователей описаны в [Cloud_Setup.md](../Cloud_Setup.md).

Офлайн здесь означает потерю связи после загрузки приложения. Установка PWA и холодная загрузка сайта без сети не добавлялись. Одновременная запись из нескольких вкладок одного профиля отдельно не проверялась.

## Шесть ручных проверок

1. **Два устройства.** На устройстве 1 открыть опубликованную версию, войти A, закончить занятие и дождаться «Сохранено в аккаунте». На устройстве 2 открыть тот же сайт, войти A и обновить историю. Сверить упражнение, руку, время и метрики; после повторного обновления и reload занятие должно остаться в одном экземпляре. При большой истории нажать загрузку следующей страницы.
2. **Офлайн после загрузки.** Войти A, отключить сеть, закончить занятие: статус ожидает синхронизации. Пока приложение доступно, вернуть сеть — статус становится подтверждённым. Повторить с reload при восстановленной сети: очередь отправляется без копии. Отдельно имитировать потерю ответа INSERT в тестовой среде — повтор должен сверить уже сохранённый итог.
3. **Гость и перенос.** Создать два гостевых занятия, войти A: автоматического импорта нет. Выбрать только одно, импортировать; повторить выбор — копии нет. Для другого адреса экспортировать JSON на старом origin, импортировать гостем на новом, затем отдельно выбрать запись для аккаунта. Невалидный файл и конфликтующий id должны отклоняться без перезаписи истории.
4. **A → B.** Задержать сеть во время отправки A, выйти и войти B, затем отпустить ответ. История и очередь A не должны появиться у B. Вернуться A и повторить синхронизацию. Проверить также задержанный ответ страницы истории.
5. **Отказ хранилища.** В тестовом браузере запретить запись localStorage/исчерпать quota, закончить занятие. Должно появиться предупреждение о памяти, без ложного обещания сохранения после reload. При доступном облаке дождаться подтверждения и проверить восстановление на втором устройстве; без подтверждения reload может потерять итог.
6. **Постоянная ошибка и конфликт.** В отдельной тестовой среде получить отказ INSERT/неподходящую схему: видна ошибка, нет бесконечных немедленных повторов и ложного подтверждения. В локальном транспортном тесте два разных payload с одним id остаются конфликтом; после исправления конфигурации кнопка повтора возобновляет допустимую отправку. Не отключать RLS для этой проверки.
